## A. Current Architecture

```
┌───────────────────────────────────────────────────────────────┐
│                     PRESENTATION LAYER                        │
│  ui/customer_cli.py          ui/management_cli.py             │
│  (input/print only — no SQL, no business logic)               │
└───────────────────────┬───────────────────────────────────────┘
                        │  calls
┌───────────────────────▼───────────────────────────────────────┐
│                      SERVICE LAYER                             │
│  auth_service.py   menu_service.py   order_service.py         │
│  inventory_service.py   analytics_service.py                  │
│  (ACID transactions, validation, orchestration)               │
└───────────────────────┬───────────────────────────────────────┘
                        │  calls
┌───────────────────────▼───────────────────────────────────────┐
│                    REPOSITORY LAYER                            │
│  customer_repo.py  inventory_repo.py  menu_repo.py            │
│  order_repo.py                                                 │
│  (raw parameterised SQL only — no business logic)             │
└───────────────────────┬───────────────────────────────────────┘
                        │  calls
┌───────────────────────▼───────────────────────────────────────┐
│                    DATABASE LAYER                              │
│  config/database.py — DatabaseManager                         │
│  MySQL 8.0+ — canteen_db                                      │
└───────────────────────────────────────────────────────────────┘
```

**Dependency flow:** Strictly top-down. No layer imports from a higher layer.  
**Data models:** Plain `@dataclass` objects in `models/` — shared across all layers with zero ORM overhead.

## C. Database Tables and Relationships

### Tables (9 total)

| Table | Primary Key | Key Columns | Notes |
|---|---|---|---|
| `Customers` | `CustomerID` AUTO_INCREMENT | `FullName`, `CustomerType` ENUM('Student','Staff'), `ContactNumber` | No email, no password |

| `DailyMenu` | `(MenuDate, ItemID)` composite | `QuantityPrepared` INT, `QuantitySold` INT | Set during morning setup |
| `Orders` | `OrderID` AUTO_INCREMENT | `CustomerID`, `ItemID`, `OrderTimestamp` DATETIME, `QuantityOrdered` INT | Written inside ACID transaction |
| `WastageLog` | `LogID` AUTO_INCREMENT | `LogDate` DATE, `ItemID`, `QuantityWasted` INT | Written at EOD |
| `Alerts` | `AlertID` AUTO_INCREMENT | `IngredientID`, `AlertTimestamp` DATETIME, `AlertType` VARCHAR(50) | Populated only by trigger |

```
Customers ──────────────────────────────────────── Orders
                                                      │

            │                        │                │
            └── DailyMenu ───────────┘                │
                   │                                   │
```

### Foreign Keys
- `MenuIngredients.ItemID` → `MenuItems.ItemID`
- `MenuIngredients.IngredientID` → `Inventory.IngredientID`
- `DailyMenu.ItemID` → `MenuItems.ItemID`
- `Orders.CustomerID` → `Customers.CustomerID`
- `Orders.ItemID` → `MenuItems.ItemID`
- `WastageLog.ItemID` → `MenuItems.ItemID`
- `Alerts.IngredientID` → `Inventory.IngredientID`

### Database Trigger
**`LowStockAlert`** — `AFTER UPDATE ON Inventory FOR EACH ROW`
Fires when `NEW.CurrentStockQuantity <= NEW.ReorderThreshold AND OLD.CurrentStockQuantity > NEW.ReorderThreshold`
Inserts a row into `Alerts` with `AlertType = 'Low Stock Warning'`

## D. Customer Workflows

### D1. Customer Identification
1. Prompted for Customer ID
2. **Returning customer path:** ID lookup via `CustomerRepository.find_by_id()` → `SELECT * FROM Customers WHERE CustomerID = %s`
3. **New registration path:** Collect Full Name, CustomerType (Student/Staff), Contact Number → `CustomerRepository.create()` → `INSERT INTO Customers` → returns new Customer with auto-assigned ID

### D2. View Menu & Place Order
1. `MenuService.get_today_menu()` → `MenuRepository.get_today_available_items(today)` → SQL JOIN of `MenuItems` + `DailyMenu` WHERE `QuantityPrepared > QuantitySold`
2. Customer selects Item ID and quantity
3. `OrderService.place_order(customer_id, item_id, quantity)` — **4-step ACID transaction**:
   - Step 1: `SELECT ... FROM DailyMenu FOR UPDATE` — lock and validate availability
   - Step 2: `SELECT ... FROM Inventory FOR UPDATE` — lock, validate, deduct each ingredient
   - Step 3: `UPDATE DailyMenu SET QuantitySold = QuantitySold + qty` — increment sold count
   - Step 4: `INSERT INTO Orders` — record the order
   - On any failure → full automatic rollback (no partial state)
4. Success/failure message returned as string to CLI

## E. Management Workflows

### E1. Authentication
- `AuthService.login(username, password)` → SHA-256 hash → `SELECT FROM Management WHERE Username = %s AND PasswordHash = %s` → returns `Manager` dataclass or `None`

### E2. Morning Setup
- `MenuService.get_all_menu_items()` → displays all items
- Manager inputs Item ID + quantity prepared
- `MenuService.set_daily_quantity(item_id, quantity)` → `MenuRepository.upsert_daily_menu()` → `INSERT ... ON DUPLICATE KEY UPDATE QuantityPrepared = QuantityPrepared + qty`
- **Note:** UPSERT accumulates quantities on repeat calls (not idempotent reset)

### E3. Inventory Monitoring
- `InventoryService.get_recent_alerts(limit=20)` → JOIN Alerts + Inventory → returns `AlertRecord` list
- `InventoryService.get_all_stock()` → SELECT all from Inventory → returns `Ingredient` list with `is_low_stock` computed property
- Optional replenishment: `InventoryService.replenish_stock(id, amount)` → validates > 0, then `UPDATE Inventory SET CurrentStockQuantity = CurrentStockQuantity + amt`

### E4. End-of-Day Wastage Logging
- `InventoryService.log_eod_wastage()`:
  1. `MenuRepository.get_daily_summary(today)` → `SELECT ItemID, QuantityPrepared, QuantitySold FROM DailyMenu WHERE MenuDate = today`
  2. For each item, compute `wasted = QuantityPrepared - QuantitySold`
  3. If `wasted > 0` AND not already logged → `OrderRepository.log_wastage()` → `INSERT INTO WastageLog`
  4. Returns count of newly inserted records — **idempotent**

### E5. Analytics — 7-Day Rolling Average
- `AnalyticsService.get_rolling_7day_wastage_forecast()` → `OrderRepository.get_rolling_7day_avg(today)`
- SQL: CTE-based window function `AVG(QuantitySold) OVER (PARTITION BY ItemID ORDER BY MenuDate ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)` — requires MySQL 8.0+
- `wastage_risk_label()` static method: "High" if `quantity_sold < avg_sold * 0.8`

### E6. Analytics — Peak-Hour Demand
- `AnalyticsService.get_peak_hour_demand()` → `OrderRepository.get_peak_hour_demand(today)`
- SQL: `SELECT HOUR(OrderTimestamp), COUNT(OrderID), SUM(QuantityOrdered) FROM Orders WHERE DATE(OrderTimestamp) = today GROUP BY HOUR ORDER BY TotalOrders DESC`

## F. Existing Business Rules

| Rule | Location | Details |
|---|---|---|
| Quantity must be > 0 for ordering | `OrderService.place_order` | Returns error string |
| Order quantity <= available portions | `OrderService` Step 1 | `FOR UPDATE` lock prevents race conditions |
| Ingredient stock must cover full order | `OrderService` Step 2 | Checked per-ingredient |
| Order is fully atomic | `OrderService` | All 4 steps in one transaction |
| Morning quantity must be > 0 | `MenuService.set_daily_quantity` | Raises `ValueError` |
| Morning item_id must be > 0 | `MenuService.set_daily_quantity` | Raises `ValueError` |
| Replenish amount must be > 0 | `InventoryService.replenish_stock` | Raises `ValueError` |
| Replenish ingredient_id must be > 0 | `InventoryService.replenish_stock` | Raises `ValueError` |
| EOD wastage is idempotent | `InventoryService.log_eod_wastage` | Skips already-logged items |
| Customer type must be Student or Staff | `CustomerCLI` | Validated in CLI, not service |
| Name cannot be empty | `CustomerCLI` | Validated in CLI, not service |
| Low-stock alert fires automatically | MySQL trigger | When stock drops at or below threshold |
| Morning UPSERT accumulates (not resets) | `menu_repo.upsert_daily_menu` | `ON DUPLICATE KEY UPDATE QuantityPrepared = QuantityPrepared + qty` |
| Password is SHA-256 hashed | `AuthService.hash_password` | Not salted — security risk |

## H. Functions That Must NOT Be Changed

> These are load-bearing, transactional, or contract-critical. Any modification risks data integrity.

1. **`DatabaseManager.transaction()`** — The entire order ACID guarantee depends on this context manager.
2. **`OrderService.place_order()`** — All 4 steps, the `FOR UPDATE` locks, and exception handling must remain intact.
3. **`InventoryRepository.deduct_stock()`** — Called inside a transaction; must use the passed cursor, not `execute_query`.
4. **`InventoryRepository.get_by_id_for_update()`** — `FOR UPDATE` is essential for preventing race conditions.
5. **`MenuRepository.get_daily_item_for_update()`** — Same reason as above.
6. **`MenuRepository.increment_quantity_sold()`** — Atomic counter increment inside transaction.
7. **`OrderRepository.create_order_in_tx()`** — Must stay inside the transaction block.
8. **`InventoryService.log_eod_wastage()`** — The idempotency check (`wastage_already_logged`) is critical.
9. **`AuthService.hash_password()`** — Changing the algorithm breaks all existing stored password hashes.
10. **`OrderRepository.get_rolling_7day_avg()`** — Complex CTE + window function; verified working on MySQL 8.0+.
11. **`DatabaseManager.initialize_schema()`** — Uses `mysql` CLI subprocess to run multi-statement SQL (required because the schema includes `DELIMITER` directives that `mysql.connector` cannot execute natively).

## J. Security Problems

| Problem | File / Location | Severity | Details |
|---|---|---|---|
| SHA-256 without salt for passwords | `auth_service.py:38-40` | HIGH | SHA-256 is fast and unsalted — vulnerable to rainbow table attacks. Should use `bcrypt` or `argon2`. |
| Password stored as plain hex digest | `Management` table | HIGH | Same issue — existing stored hashes are all equivalent SHA-256 |
| No customer authentication | `customer_repo.py`, `customer_cli.py` | HIGH | Customers are identified by integer ID only. Anyone who knows a customer ID can order as them. |
| DB credentials prompted at runtime via `getpass` | `main.py:50-65` | MEDIUM | Correct for CLI but will block a web server. Must be moved to environment variables or `.env` file. |
| No input sanitisation in CLI | `customer_cli.py`, `management_cli.py` | MEDIUM | All SQL is parameterised (safe from SQL injection), but customer type validation only in CLI — not service layer. |
| CustomerType validation only in UI layer | `customer_cli.py:67-70` | MEDIUM | Service layer doesn't validate; a direct service call with invalid type would succeed. |
| No HTTPS enforcement | N/A (CLI app) | MEDIUM | Relevant once web-hosted — credentials will travel over HTTP without TLS. |
| `package.json` in project root | root | LOW | npm init was run; `node_modules/` may appear if npm install is run — no entry in `.gitignore` for it. |
| No SECRET_KEY / session signing | N/A (CLI app) | HIGH | A web layer will need Flask session signing key. |

| Problem | Location | Severity | Details |
|---|---|---|---|
| No unique constraint on CustomerType enforced at app layer | `customer_repo.py` | MEDIUM | DB uses ENUM ('Student','Staff'), but CustomerRepository.create() does not validate — relies on CLI |

## M. Recommended Web Architecture

### Technology Stack

| Layer | Technology | Reason |
|---|---|---|
| Web framework | Flask (Python) | Minimal, fits existing Python stack, easy DI wiring |
| Template engine | Jinja2 (Flask built-in) | Server-side rendering, no extra dependency |
| CSS | Vanilla CSS | Full control, no build step |
| Charts | Chart.js (CDN) | Zero build, works with JSON API responses |
| JS | Vanilla JS | Fetch API for AJAX, no framework overhead |
| Sessions | Flask sessions (signed cookie) | Customer and manager session tracking |
| DB connections | `MySQLConnectionPool` | Replace single connection with thread-safe pool |
| Config | `.env` file + `python-dotenv` | Move DB credentials out of runtime prompts |
| Password hashing | `bcrypt` (optional upgrade) | Replace SHA-256 |

### Minimal Required Changes to Existing Code
1. **`DatabaseManager`**: Add `MySQLConnectionPool` support alongside existing `connect()`/`disconnect()`
2. **`AuthService.seed_admin_if_needed`**: Remove `input()`/`getpass()` — accept params, or make it a CLI-only utility
3. **`InventoryService.replenish_stock`**: Accept `float` in addition to `Decimal` (web forms return strings/floats)
4. **Add JSON serialisation helpers**: Convert `Decimal` to `float`, `datetime` to ISO string, in a utility module
5. **Move CustomerType validation** into `CustomerRepository.create()` or a new `CustomerService`
